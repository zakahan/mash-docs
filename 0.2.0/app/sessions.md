# 会话与多轮对话

以报告助手为例，同一用户可能同时查看季度报告和采购清单。应用可为两段对话分别创建会话，将返回的 ID 保存在各自的对话记录里。打开季度报告页面时，消息历史和新的追问都使用报告对应的 ID。

| 标识 | 使用位置 | 如何选择 |
|---|---|---|
| `app_name` | 会话路由、流式调用 | 从当前 Runtime 的 `GET /list-apps` 获取。 |
| `user_id` | 会话路由、执行请求 | 使用业务系统中稳定的用户标识。调用入口的鉴权仍按 Runtime 要求处理。 |
| `session_id` | 会话详情、执行请求 | 使用创建会话响应中的 `id`，为每段独立对话保存一份。 |

## 从空会话开始或恢复已有会话

1. `POST /apps/{app_name}/users/{user_id}/sessions`，提交 `{}` 让服务分配 ID；也可以提交 `{"id":"report-q1"}` 指定 ID。
2. 消息发送到 `/run_sse` 后，服务端以相同的用户和会话标识读写上下文。
3. 页面重新加载时，请求 `GET /apps/{app_name}/users/{user_id}/sessions/{session_id}`，从详情恢复历史。用户回到会话目录时，使用同一路径去掉最后的会话 ID 来查询列表。
4. 如果详情返回 404，检查三个标识和目标 Runtime。会话使用的后端决定重启及跨实例访问时历史是否可见，见[高级配置](advanced.md)。

## 初始状态和事件

创建会话支持初始 `state`，适合存放应用后续需要读取的键值，例如 `{"state":{"report_id":"q1"}}`。业务需要模型理解的内容应显式通过指令、消息或工具提供。导入已有对话时可以提交 `events`；服务逐个按 ADK Event 格式校验并追加。普通聊天从空历史开始即可。

启用会话元数据后，列表和详情还提供运行状态和标题。流开始时会话可进入 `running`，正常结束后回到 `idle`，执行异常可标记为 `error`。客户端重连时先查详情，能将上一轮已保存的事件和当前状态一并恢复。详情查询与再发一次消息是两个不同的操作；重复提交会发起新的执行。
